# Iteration procedure

1. Confirm the current roster revision and hard locks. The current roster is a reference point, not a preferred answer.
2. If the player has used it, collect a short debrief before proposing changes:
   - What worked and should be preserved?
   - What did not work or failed to earn its cost?
   - What felt awkward, unreliable, or unfun?
   - Where did scoring, target access, durability, or killing power fail?
   - Which borrowing, proxy, purchase, painting, or transport costs matter?
3. Convert the debrief and tournament goal into explicit success criteria. Separate repeated observations from one-game variance and rules mistakes.
4. Select the highest-impact unresolved decision. When several reported failures share a cause, treat the affected package as one decision rather than forcing artificial one-unit steps.
5. Define a small set of decision-relevant field scenarios from separate evidence streams.
6. Compare the incumbent fairly against the smallest focused tune that addresses the criteria. Include a coherent package change or rebuild when the player invites one or the incumbent structurally misses the criteria.
7. Resolve complete consequences for every live alternative: points, inventory, readiness, roles, mission pieces, dependencies, and failure modes.
8. Crunch only target/package cases that distinguish live alternatives. Audit both attacker and defender effects.
9. Present gains, losses, access assumptions, resource conflicts, unsupported mechanics, forecast sensitivity, and which debrief criteria each alternative does or does not address.
10. Ask for accept, reject, revise, or defer.
11. Apply only to the proposal's base revision. Reconcile stale proposals instead of replaying them.
12. Recompute affected checks and combat reports; retain rejected reasons and open questions.

A productive result may retain the incumbent or specify a practice game. Retention is a conclusion, not a default. Popularity is evidence of use, not proof of causal strength.
