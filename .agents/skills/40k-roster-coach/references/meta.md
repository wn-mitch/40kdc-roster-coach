# Local meta procedure

Create an event record before evidence records. Use stable local aliases for people; keep names and private notes only in the ignored workspace.

## Source order

1. User-supplied store, locality, event, and list links, plus firsthand scouting and match reports.
2. Listhammer location, faction, stats, event, player-history, and list pages.
3. Saved exports or pasted extracts.
4. BCP or another event platform through an authorized signed-in browser tab, only for active-event facts unavailable above.

BCP is not required for venue history or regular-attendee discovery when Listhammer exposes those records.

## Venue regulars

When the player identifies a local store and asks to “pull the regulars,” do not require an event link or a list of names.

1. Resolve the venue through Listhammer's supported location query when available. If the store name is ambiguous, ask for only the city or the correct search result. Never depend on an undocumented endpoint.
2. Gather events at that exact venue. State the date window; default to the most recent 12 months when the player gives none.
3. Define a regular before counting. Default to at least two appearances at that venue in the window. Keep one-off visitors separate.
4. Complete a breadth-first pass across every discovered regular before selecting exemplar lists. Report total attendees, matched regulars, unmatched attendees, history coverage, and list coverage.
5. Store identities only in the ignored private workspace and use stable aliases in durable evidence.
6. For each regular, record attendance count, observed factions by date, latest result, and format. Then retrieve decision-relevant lists; do not substitute a few armor-heavy or high-finishing examples for the field pass. Faction history is a tendency, not a commitment for the next event.
7. Keep the venue denominator and unobserved remainder explicit. Deduplicate repeat event pages and mirrored results.
8. Use BCP only if the player separately asks to inspect active registration or submitted rosters and authorizes the browser tab.

Browser access is observational. Never enter credentials, change registration, submit a roster, message a player, or publish a link without explicit direction.

## Normalization

Every record keeps original wording, interpreted claim, stream, source locator, confidence, event applicability, attendance status, roster commitment, optional subject/event references, scenario tags, and sample limitations. Missing values remain missing or unknown.

Treat firsthand reports as evidence, not claims that require public corroboration before use. External records calibrate scope and uncertainty; they do not overrule the player's account of their own games or local expectations.

Listhammer list coverage is partial and biased toward strong finishes. A retrieved-list sample can demonstrate existence or suggest a pattern; it cannot establish field frequency without field data. Keep RTT inclusion, dates, rules period, singles/team format, denominator, and retrieval time.

## Synthesis

Run `meta report EVENT_ID`. Interpret its scenario signals rather than collapsing them into one probability. Distinguish confirmed attendance from possible attendance. Do not count one subject twice because several archetypes remain possible. If field size is known, report the unscouted remainder; otherwise state that the denominator is unavailable.
